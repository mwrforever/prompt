# 项目宪法生成器（AGENTS.md）

> 职责：基于项目的技术栈，派发 subagent 调研各技术栈的官方文档与厂商最佳实践，把调研结果提炼为一份「只存原则、约束与数据契约」的项目宪法文件 `AGENTS.md`，结构风格见 `references/example.md`。调研一律派遣 subagent 执行，主控代理只做编排（输入锁定、派遣协调、报告评审、章节合成、审核派遣、落盘）。

## 一、何时使用

- 用户要"根据技术栈生成项目宪法 / AGENTS.md / 项目规范文件"
- 用户要求"派发 subagent 调研各大厂商对该技术栈的最佳实践后产出一份规范"
- 用户贴出示例（如 MindSoar AGENTS.md 那种四段结构）要求"生成类似的宪法"
- 用户给出技术栈清单，要求"写成供编码代理执行的约束规范"

## 二、输入收集（一次问齐，不反复打扰）

| 输入 | 说明 | 缺省 |
|---|---|---|
| 项目名与定位 | 一句话业务描述（如"基于时间线感知的漏斗式映射系统"） | 当前工作区目录名 |
| 技术栈清单 | 按域给出：语言 / Web 框架 / ORM / 数据库 / 缓存 / 消息队列 / 图数据库 / agent 框架 / LLM 网关 / 前端 / 构建与 CI；可粘贴或指向配置文件（pyproject.toml、package.json 等）；未提供时派遣「项目勘察」subagent 扫描项目根推断 | 必填，缺失才问或勘察 |
| 全局约束文件 | 是否引用已有全局 AGENTS.md/CLAUDE.md（如 `~/.zcode/AGENTS.md`）——宪法只引用其注释/日志/测试规范段落，不重复正文；缺失时探测常见全局位置，找不到则不引用 | 探测常见全局位置，无则不引用 |
| 项目特有材料 | 数据模型、图模型、映射关系、既有架构/设计文档路径 | 无 |
| 输出位置 | `<目标项目根>/AGENTS.md` | 当前工作区 |
| 修订模式 | 目标已存在 AGENTS.md → 默认另存 `AGENTS.md.draft`；或用户明确要求覆盖（覆盖前须先备份旧文件） | 另存 draft |

- 引用全局约束文件时，宪法头部引用的章节号必须与该文件实际章节一致（先读该文件核对再写入宪法）。
- 技术栈版本一律以用户提供或勘察到的 lockfile/配置文件实测为准，禁止编造。

## 三、技术栈分域与调研主题划分（不过度拆分）

调研主题按技术栈组件族生成，**强耦合组件合并为一题**（语言+Web 框架、ORM+迁移+数据库、缓存+消息流各一题），避免拆到单个库：

| 典型主题 | 覆盖组件 | 宪法段落落点 |
|---|---|---|
| 语言 + Web 框架 | 如 Python 3.12 + FastAPI | A.1 编码约束 / A.3 API 设计 |
| ORM + 迁移 + 数据库 | 如 SQLAlchemy 2.0 + Alembic + PostgreSQL | A.4 数据库操作 |
| 缓存 + 消息队列 | 如 Redis + Stream/消费组 | A.5 基础设施生命周期 |
| 图数据库 | 如 Neo4j（节点/关系/查询规则） | D.4/D.5 数据契约 |
| 架构 / agent 框架 | 如 LangGraph（图 / checkpoint / HITL / 运行时） | Part B 全部 |
| LLM / 媒体网关 | 如 litellm + 厂商 SDK + 模型注册表 | B.4 网关 |
| 前端框架 + UI 栈 | 如 Next.js + TS + Tailwind + UI 组件库 | Part C 全部 |
| 构建 + 测试 + CI 门禁 | 如 uv / ruff / pytest / pre-commit / Actions | A.6 或附录 |
| 部署 / 容器（可选） | Docker / 编排 / 对象存储 | A.5 或附录 |

- 主题数 = 宪法段落一一对应；项目无对应组件则不生成该主题、宪法省略对应段落（Part B/C 整体可按实际省略，Part D 必有）。
- 每主题的调研范围（按优先级检索，来源必须真实可查，禁止编造）：
  1. **官方文档**（第一来源）：语言 / 框架 / 中间件的官方文档、官方迁移指南、官方 production/部署指南
  2. **厂商最佳实践**（第二来源）：技术栈所属厂商或头部厂商公开的工程实践规范——如 Vercel（Next.js）、Astral（uv/ruff）、LangChain（LangGraph）、Redis 官方、GitHub（CI 实践）、Anthropic（agent 工程实践）等
  3. **权威社区聚合**（第三来源）：框架官方推荐的 best-practice 指南与聚合页
- 检索不到的条目记 `{待调研项}` + 原因，禁止用记忆中的"常见规范"充数。

## 四、核心工作流（顺序执行）

1. **输入锁定**：按 §二 一次问齐；技术栈未提供时，先派遣「项目勘察」subagent（扫描项目根：pyproject.toml / package.json / Cargo.toml / lockfile / .env.example / docker-compose 等，输出技术栈清单 + 配置证据路径）。
2. **调研派遣**：按 §三 主题表生成调研任务清单，**并行派遣**（每个主题一个调研专员；平台不支持 subagent 派遣时按主题逐轮执行，每轮独立完成"检索 → 报告"闭环）。每次派遣必须含 §五 五要素。
3. **报告评审（主控）**：收齐报告后逐份检查——规范条目与来源一一对应、URL 真实可查、无编造；不合格退回对应调研专员补齐（≤2 轮，超限升级用户）。把「全局约束文件」实际章节号核对后写入宪法头注。
4. **章节合成（主控）**：按 `references/template.md` 骨架把调研报告提炼为**原则级条款**——只存原则、约束与数据契约，不写实现细节；跨主题冲突以「官方文档 > 厂商实践 > 社区实践」裁决并注明；段落按实际技术栈裁剪。
5. **审核派遣**：指派「审核专员」subagent 对照 `references/template.md` 与 `references/example.md` 审核 draft 宪法（结构完备、无编造、无实现细节、无重复全局规范正文）；不通过则主控修订后复审（≤2 轮，超限升级用户）。
6. **落盘**：写入 `<目标项目根>/AGENTS.md`（已存在 → 默认 `AGENTS.md.draft`，用户明确要求覆盖时先备份旧文件）；UTF-8 无 BOM、LF 行尾。调研报告落盘 `<目标项目根>/docs/agmds-research/{yyyy-MM-dd}-{主题}.md`。
7. **汇报**：段落结构概览（Part A–D 与调研主题对照）、调研报告路径清单、`{待调研项}` 登记、修订指引（宪法后续修订须按 D.6 记变更记录）。

## 五、调研派遣五要素（每次派遣必含）

```markdown
【角色】调研专员——{主题}（每个调研主题一个，单一职责）
【输入】技术栈组件清单 + 实际版本 + 项目上下文（禁止模糊指代）
【职责】检索官方文档与厂商最佳实践，产出规范候选条目；不做实现、不做取舍决策
【输出】`docs/agmds-research/{yyyy-MM-dd}-{主题}.md`：技术概况 + 规范候选表（规范条目 | 依据 | 来源 URL | 适用版本 | 取舍建议）
【完成标准】规范条目与来源一一对应、URL 真实可查、无编造；检索不可得条目标 `{待调研项}` 并注明原因
```

**并行规则**：无依赖主题的调研并行派遣；报告评审 → 合成 → 审核 → 落盘严格串行。

## 六、产出要求

- 路径：`<目标项目根>/AGENTS.md`；副产物调研报告 `<目标项目根>/docs/agmds-research/{date}-{topic}.md`
- 结构：完整套用 `references/template.md` 章节骨架，逐章填写，禁止缺章；Part B/C 按技术栈实际省略
- 内容：只存原则、约束与数据契约，每条可验证；语言：中文；编码 UTF-8 无 BOM、LF 行尾
- 占位符：`{待调研项}` 集中于宪法附录「待回填登记表」登记并汇报，禁止编造
- 引用不重复：全局约束文件已有段落只引用（含章节号）不复制正文

## 七、反模式（禁止）

- ❌ 编造厂商规范或来源 URL → 每条规范必须真实可溯源（调研报告）
- ❌ 主控亲自调研 → 调研一律派遣 subagent（§四.2），主控只编排与合成
- ❌ 重复全局 AGENTS.md 已有规范正文 → 引用不重复
- ❌ 写入实现细节 → "怎么实现"留给代码与 TASK.md
- ❌ 无技术栈依据凭空写约束 → 版本与规范必须来自用户提供或勘察证据
- ❌ 目标已存在 AGENTS.md 不确认直接覆盖 → 默认另存 draft
- ❌ 产物仅存于对话不落盘
