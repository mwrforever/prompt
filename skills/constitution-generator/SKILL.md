# 项目宪法生成器（AGENTS.md）

> 职责：基于项目的技术栈，派发 subagent 调研各技术栈的官方文档与厂商最佳实践，把调研结果提炼为「只存工程原则与约束」的**分层宪法文档体系**：
> - **根定位层**：根 `<目标项目根>/AGENTS.md` 只做项目定位、**根目录一层**目录地图、命令总览、**强制阅读路由**（写某子项目代码必读其宪法）、子项目宪法**索引**与跨切约定总则，不承载任何子项目内部的深度约束；
> - **子项目宪法**：每个技术子项目目录（如 `backend/`、`frontend/`）各生成 `<子项目>/AGENTS.md`，承载该子项目的全部宪法深度；业务功能设计与数据契约不写入，只留指向 `specs/` 的职责行；
> - **配套 CLAUDE.md**：每份 AGENTS.md 同目录配套生成一份 `CLAUDE.md`，以 md 链接索引该 AGENTS.md（根 CLAUDE.md 另列出全部子宪法与配套文件链接），保证以 CLAUDE.md 为入口的工具可达宪法体系；CLAUDE.md 为纯索引，不写规范正文。
>
> 定位层与子宪法的书面风格见 `references/example.md`。调研一律派遣 subagent 执行，主控代理只做编排（输入锁定、子项目判定、派遣协调、报告评审、章节合成、审核派遣、落盘）。

## 一、何时使用

- 用户要"根据技术栈生成项目宪法 / AGENTS.md / 项目规范文件"
- 用户要求"派发 subagent 调研各大厂商对该技术栈的最佳实践后产出一份规范"
- 用户贴出示例（根一层目录地图 + 子项目宪法索引的分层规范）要求"生成类似的宪法"
- 用户要求"前后端约束分开 / 根目录只做索引 / monorepo 各模块一份规范"
- 用户给出技术栈清单，要求"写成供编码代理执行的约束规范"

## 二、输入收集（一次问齐，不反复打扰）

| 输入 | 说明 | 缺省 |
|---|---|---|
| 项目名与定位 | 一句话业务描述 | 当前工作区目录名 |
| 技术栈清单 | 按**子项目**分域给出：语言 / Web 框架 / ORM / 数据库 / 缓存 / 消息队列 / 图数据库 / agent 框架 / LLM 网关 / 前端 / 构建与 CI；可粘贴或指向配置文件（pyproject.toml、package.json 等）；未提供时派遣「项目勘察」subagent 扫描项目根推断 | 必填，缺失才问或勘察 |
| 子项目清单 | 根目录一层内带独立依赖清单（pyproject.toml / package.json / go.mod 等）的技术子项目目录与各自职责（如 backend=API 网关、frontend=Web UI）；非技术目录（docs/、scripts/、docker/）不入宪法体系，只在根目录地图标注。**整仓单应用**（依赖清单位于仓库根、无并列技术子目录）视作唯一子项目：只产出该子项目宪法（落 `<根>/AGENTS.md`），不另生成定位层 | 勘察判定 |
| 全局约束文件 | 是否引用已有全局 AGENTS.md/CLAUDE.md（如 `~/.zcode/AGENTS.md`）——宪法只引用其注释/日志/测试规范段落，不重复正文；缺失时探测常见全局位置，找不到则不引用 | 探测常见全局位置，无则不引用 |
| 项目特有材料 | 既有架构/设计文档（`specs/` 等）路径——子宪法只引用其路径与职责，不复制内容 | 无 |
| 行数与去重要求 | 定位层 ≤ 200 行（默认）、每份子宪法各 ≤ 500 行（默认）；超限必须精简：砍重复、实现细节、功能设计；同一规则全篇只落一处，其余交叉引用 | 200 / 500 |
| 登记/变更文件 | 待回填登记表落 `TASK.md`、变更记录落 `CHANGELOG.md`（项目已有则沿用，无则新建；**均为根级**，各子宪法共用）；定位层与子宪法头注以「配套文件职责」列明各文件边界；**宪法正文不设变更控制/变更记录章节** | 外置 TASK.md / CHANGELOG.md |
| 输出位置 | `<目标项目根>/AGENTS.md`（定位层）+ `<子项目>/AGENTS.md` ×N（子宪法）；整仓单应用时仅 `<根>/AGENTS.md`。每份 AGENTS.md 同目录配套生成 `CLAUDE.md`（md 链接索引，见 §六） | 当前工作区 |
| 修订模式 | 目标已存在任一 AGENTS.md 或配套 CLAUDE.md → 默认另存 `AGENTS.md.draft` / `CLAUDE.md.draft`；或用户明确要求覆盖（覆盖前须先备份旧文件） | 另存 draft |

- 引用全局约束文件时，宪法头部引用的章节号必须与该文件实际章节一致（先读该文件核对再写入）；定位层与各子宪法的全局引用必须同源同章节号。
- 技术栈版本一律以用户提供或勘察到的 lockfile/配置文件实测为准，禁止编造。

## 三、技术栈分域与调研主题划分（不过度拆分）

调研主题按技术栈组件族生成，**强耦合组件合并为一题**（语言+Web 框架、ORM+迁移+数据库、缓存+消息流各一题），避免拆到单个库：

| 典型主题 | 覆盖组件 | 子宪法段落落点 |
|---|---|---|
| 语言 + Web 框架 | 如 Python 3.12 + FastAPI | A.1 编码约束 / A.3 API 设计 |
| ORM + 迁移 + 数据库 | 如 SQLAlchemy 2.0 + Alembic + PostgreSQL | A.4 数据库操作 |
| 缓存 + 消息队列 | 如 Redis + Stream/消费组 | A.5 基础设施生命周期 |
| 图数据库 | 如 Neo4j（连接 / 查询 / 生命周期约束） | A.5 基础设施生命周期；业务图模型契约归 `specs/` 职责行 |
| 架构 / agent 框架 | 如 LangGraph（图 / checkpoint / HITL / 运行时） | Part B 全部 |
| LLM / 媒体网关 | 如 litellm + 厂商 SDK + 模型注册表 | B.4 网关 |
| 前端框架 + UI 栈 | 如 Next.js + TS + Tailwind + UI 组件库 | 前端子宪法 A.1 编码约束 / B 架构分层 |
| 构建 + 测试 + CI 门禁 | 如 uv / ruff / pytest / pre-commit / Actions | 各子宪法 A.6 或 C.4；门禁总则（原则级 1–3 条）落定位层「跨切约定」 |
| 部署 / 容器（可选） | Docker / 编排 / 对象存储 | A.5 或附录 |

- 主题数 = 子宪法段落一一对应；子项目无对应组件则不生成该主题、省略对应段落（Part B 整体可按实际省略，Part C 必有）。
- **主题归属**：每个主题归属其组件所在的**子项目宪法**——后端族主题（语言+Web 框架、ORM+数据库、缓存+消息、架构/agent、网关）落对应后端子宪法；前端族主题（前端框架 + UI 栈）落前端子宪法；跨子项目主题（构建 + 测试 + CI 门禁、部署）只把**门禁总则**落根定位层「跨切约定」，各语言工具链细节落对应子宪法。派遣调研专员时在【输入】中标注归属。
- 每主题的调研范围（按优先级检索，来源必须真实可查，禁止编造）：
  1. **官方文档**（第一来源）：语言 / 框架 / 中间件的官方文档、官方迁移指南、官方 production/部署指南
  2. **厂商最佳实践**（第二来源）：技术栈所属厂商或头部厂商公开的工程实践规范——如 Vercel（Next.js）、Astral（uv/ruff）、LangChain（LangGraph）、Redis 官方、GitHub（CI 实践）、Anthropic（agent 工程实践）等
  3. **权威社区聚合**（第三来源）：框架官方推荐的 best-practice 指南与聚合页
- 检索不到的条目记 `{待调研项}` + 原因，禁止用记忆中的"常见规范"充数。

## 四、核心工作流（顺序执行）

1. **输入锁定 + 项目勘察**：按 §二 一次问齐；技术栈或子项目清单未提供时，派遣「项目勘察」subagent 扫描项目根（pyproject.toml / package.json / go.mod / Cargo.toml / lockfile / .env.example / docker-compose 等配置证据），输出：① 技术栈清单（按子项目分域）+ 配置证据路径；② **子项目清单**——根目录一层内所有带独立依赖清单的目录及各自技术栈与职责；整仓单应用时注明"唯一子项目，宪法落仓库根"。清单回报用户确认（用户已指定则跳过确认）。
2. **调研派遣**：按 §三 主题表生成调研任务清单（每题标注归属：定位层跨切 / 某子宪法），**并行派遣**（每个主题一个调研专员；平台不支持 subagent 派遣时按主题逐轮执行，每轮独立完成"检索 → 报告"闭环）。每次派遣必须含 §五 五要素。
3. **报告评审（主控）**：收齐报告后逐份检查——规范条目与来源一一对应、URL 真实可查、无编造；不合格退回对应调研专员补齐（≤2 轮，超限升级用户）。把「全局约束文件」实际章节号核对后写入头注。
4. **章节合成（主控）**：按 `references/template.md` 对应模板把调研报告提炼为**原则级条款**——只存工程原则与约束，不写实现细节；跨主题冲突以「官方文档 > 厂商实践 > 社区实践」裁决并注明；段落按实际技术栈裁剪。**先合成根定位层**（项目定位 + 一层目录地图 + 命令总览 + 强制阅读路由 + 子项目宪法索引 + 跨切约定 + 配套文件职责，≤ 定位层上限；子项目内部结构一律不展开，只标「规范见 <子项目>/AGENTS.md」）；**再逐子项目合成子宪法**（头注反指定位层与全局规范，内容只管本子项目深度）；**最后生成配套 CLAUDE.md**（每份 AGENTS.md 一份，md 链接索引该 AGENTS.md；根 CLAUDE.md 另列出全部子宪法与 TASK.md / CHANGELOG.md 链接）。合成后自查五项：① 各文档行数 ≤ 对应上限（超限必须砍重复/实现细节/功能设计）；② 全篇同一规则只落一处，其余交叉引用（含对全局约束文件、定位层 ↔ 子宪法的引用）；③ **功能设计边界**——业务数据模型、图模型节点/关系清单、状态机事件、业务计算规则一律不写入，只留指向 `specs/` 的职责行；④ **归属正确**——子项目约束不串写（前端约束只在前端子宪法、后端约束只在后端子宪法），定位层无任何子项目深度约束；⑤ **入口可达**——定位层文档头含「写 {子项目} 代码必读 <子项目>/AGENTS.md」强制路由且与索引一一对应，各配套 CLAUDE.md 链接与实际文件一一对应。
5. **审核派遣**：指派「审核专员」subagent 对照 `references/template.md` 与 `references/example.md` 审核**全部**文档（结构完备、无编造、无实现细节、无业务功能设计细节混入、无重复全局规范正文、**引用链一致**——定位层索引的路径与职责描述和子宪法实存一一对应、子宪法头注反指定位层、配套 CLAUDE.md 均为 md 链接且路径可达）；不通过则主控修订后复审（≤2 轮，超限升级用户）。
6. **落盘**：`<目标项目根>/AGENTS.md`（定位层）+ 各 `<子项目>/AGENTS.md`（子宪法）+ 配套 `CLAUDE.md` ×(N+1)（md 链接索引）；整仓单应用时仅 `<根>/AGENTS.md` + `<根>/CLAUDE.md`。已存在 → 默认 `*.draft` 另存（各文件分别处理），用户明确要求覆盖时先备份旧文件；UTF-8 无 BOM、LF 行尾。副产物（均根级）：调研报告 `<目标项目根>/docs/agmds-research/{yyyy-MM-dd}-{主题}.md`、待回填登记表 `<目标项目根>/TASK.md`（无 TASK.md 时按模板附录内嵌子宪法）、变更记录 `<目标项目根>/CHANGELOG.md`（追加式，保留既有历史）。
7. **汇报**：文档体系概览（子项目清单、AGENTS.md 与配套 CLAUDE.md 各文件路径与行数、定位层索引 ↔ 子宪法对照表）、调研报告路径清单、`{待调研项}` 登记、修订指引（宪法后续修订须先在 `CHANGELOG.md` 记变更记录再改正文；修订涉及定位层与子宪法时同步更新索引、强制阅读路由与引用链）。

## 五、调研派遣五要素（每次派遣必含）

```markdown
【角色】调研专员——{主题}（每个调研主题一个，单一职责）
【输入】技术栈组件清单 + 实际版本 + 项目上下文 + 归属文档（定位层跨切 / 某子宪法）（禁止模糊指代）
【职责】检索官方文档与厂商最佳实践，产出规范候选条目；不做实现、不做取舍决策
【输出】`docs/agmds-research/{yyyy-MM-dd}-{主题}.md`（报告头标注题归属文档）：技术概况 + 规范候选表（规范条目 | 依据 | 来源 URL | 适用版本 | 取舍建议）
【完成标准】规范条目与来源一一对应、URL 真实可查、无编造；检索不可得条目标 `{待调研项}` 并注明原因
```

**并行规则**：无依赖主题的调研并行派遣；报告评审 → 合成 → 审核 → 落盘严格串行。

## 六、产出要求

- 路径：`<目标项目根>/AGENTS.md`（定位层）+ `<子项目>/AGENTS.md` ×N（子宪法）+ 配套 `CLAUDE.md` ×(N+1)；整仓单应用时仅 `<根>/AGENTS.md` + `<根>/CLAUDE.md`；副产物（根级）：调研报告 `<目标项目根>/docs/agmds-research/{date}-{topic}.md`、登记表 `<目标项目根>/TASK.md`、变更记录 `<目标项目根>/CHANGELOG.md`
- 结构：定位层与子宪法分别完整套用 `references/template.md` 对应模板，逐章填写，禁止缺章；子宪法 Part B 按技术栈实际省略；有 TASK.md / CHANGELOG.md 时附录与变更记录外置，头注「配套文件职责」指向
- **强制阅读路由**：定位层文档头必含「写后端代码必读 `backend/AGENTS.md`、写前端代码必读 `frontend/AGENTS.md`」强制路由（按实际子项目列全），与子项目宪法索引一一对应；配套 CLAUDE.md 以 md 链接复现该路由
- **分层规则**：定位层只描述**根目录一层**目录结构与索引，子项目内部目录与深度约束禁止写入；根级配套文件（TASK.md / CHANGELOG.md）在仓库地图与跨切约定中标注职责；子项目约束归其子宪法；跨切约定只写总则，细节归对应子宪法
- **配套 CLAUDE.md**：每份 AGENTS.md 同目录一份 `CLAUDE.md`，以 md 链接索引该 AGENTS.md；根 CLAUDE.md 另列出全部子宪法与 TASK.md / CHANGELOG.md 链接；纯索引，不写规范正文，不与 AGENTS.md 重复内容
- 内容：只存工程原则与约束，每条可验证；语言：中文；编码 UTF-8 无 BOM、LF 行尾；各文档正文 ≤ 对应行数上限（定位层 200 / 子宪法 500 默认）；全篇无重复描述
- **功能设计边界**：业务数据模型、图模型节点/关系清单、状态机事件、业务计算规则等**一律禁止写入**，只留指向 `specs/` 的职责行
- **变更记录外置**：宪法正文不设变更控制/变更记录章节，修订流程 = 先记 `CHANGELOG.md` 再改正文，语义由头注「配套文件职责」承载
- 占位符：`{待调研项}` 集中于 TASK.md「待回填登记表」（无 TASK.md 时内嵌子宪法附录）登记并汇报，禁止编造
- 引用不重复：全局约束文件已有段落只引用（含章节号）不复制正文；定位层与子宪法之间引用链互通但不重复正文

## 七、反模式（禁止）

- ❌ 编造厂商规范或来源 URL → 每条规范必须真实可溯源（调研报告）
- ❌ 主控亲自调研 → 调研一律派遣 subagent（§四.2），主控只编排与合成
- ❌ 重复全局 AGENTS.md 已有规范正文 → 引用不重复
- ❌ 子项目内部结构 / 深度约束写进根定位层 → 定位层只做一层目录地图 + 索引 + 跨切总则（§六分层规则）
- ❌ 定位层缺强制阅读路由（写某子项目代码必读其宪法）或路由与宪法索引不一致 → 文档头必含、一一对应（§六强制阅读路由）
- ❌ 配套 CLAUDE.md 缺失、未用 md 链接语法、链接路径失效或写了规范正文 → §六配套 CLAUDE.md 规则，审核专项核对（§四.5）
- ❌ 前端约束写进后端子宪法（或反之）→ 约束归属其子项目宪法（§四.4 自查④）
- ❌ 定位层索引与子宪法实际路径 / 职责描述不一致 → 审核派遣专项核对（§四.5）
- ❌ 定位层与子宪法重复同一规则正文 → 同一规则只落一处，其余交叉引用
