# 交付 Loop/Graph 设计器

> 本 skill 的职责：把用户的「需求」或「已定项 spec」（可多份）转化为一份**生产规范化**的交付执行文档（loop 或 graph 形态），文档落盘于 `<目标项目根>/docs/prompt/{yyyy-MM-dd}-{loop|graph}-{任务标题}.md`。文档为纯 Markdown 执行指令，规定调研、实现、审核均由 subagent 派遣执行，主控代理仅编排。

## 一、何时使用

- 用户要"设计一个交付 loop / graph / 端到端执行流程 / 分阶段落地计划"
- 用户给出一份 spec（文件路径或粘贴全文），要求"按它产出执行文档"
- 用户要求"像上次那份执行文档一样"设计执行方案（风格参照 `references/example.md`）
- 用户提到阶段门禁、DoD、中止条件、修复循环、升级用户决策、派遣 subagent 规范等概念

## 二、输入收集（一次问齐，不反复打扰）

| 输入 | 说明 | 缺省 |
|---|---|---|
| 任务目标与范围 | 做什么、边界在哪 | 必填，缺失才问 |
| 输入形态 | 已定项 spec（一份或多份）或 需求描述（一条或多条），可混合提供 | 按用户实际输入判断 |
| 参考信息 | 代码目录、文档、设计稿、链接等 | 无 |
| 实现要求 | 技术栈、编码规范、质量门禁、测试要求 | 无（不得编造） |
| 目标项目根 | 文档落盘位置 | 当前工作区 |

- **定项模式**：用户给了已定项的 spec（可多份）→ **每份 spec = 一个任务**，任务是 spec 级别的执行单元，只做任务清单编列与依赖排布，**不重设计、不把一份 spec 拆成多个任务**。
- **需求模式**：只有需求（可多条）→ 按**复杂性模块化**拆分为多个任务（复杂需求拆成多个模块任务，多条简单需求可合并），**不过度拆分**；拆分依据写入文档 1.3 节。

## 三、形态选择：loop 还是 graph

| 形态 | 判定依据 | 特征 |
|---|---|---|
| `loop` | 阶段单向序贯、依赖线性、无并行轨道 | 主控循环 + 阶段门禁 + 修复循环 |
| `graph` | 存在 ≥2 条相互独立、可并行的工作流（多端并行、多主题调研、前后端并行） | 节点 DAG + 并行分支 + 汇合门禁 + 依赖边与回退边 |

- 选择规则：**有独立可并行分支用 graph，否则用 loop**；graph 文档仍保留主控循环（总进度判定），并行发生在阶段/节点内部。
- 文件名中的 `{loop|graph}` 与所选形态一致。

## 四、核心工作流（顺序执行）

1. **目标设定**：一句话任务目标 + 可验证的 Definition of Done 清单（每条须附证据要求）。
2. **范围定义**：In Scope / Out of Scope 编号清单；Out of Scope 含"本次明确不做"项。
3. **任务拆分**：
   - 定项模式：**一份 spec = 一个任务**——多份 spec 则任务清单 = spec 清单（T1=spec1、T2=spec2…），验收标准取自对应 spec，不重设计、不进一步拆分。
   - 需求模式：按**复杂性模块化**拆分——先做功能域分解，按业务能力内聚拆为若干模块任务；**不过度拆分**：单任务可在一次 subagent 派遣周期内完成"调研 → 实现 → 审核"闭环即可，相邻强耦合模块合并为一个任务。
   - 拆分依据写入文档 1.3 节（定项模式仅一行声明，见模板）。
4. **阶段设计**（标准骨架，按任务裁剪）：
   `P0 环境与准备 → 调研/设计 → 审核 → 实现（TDD/集成） → 端到端验收 → 终验`
   每阶段必须给出：目标、核心产物（落盘路径）、步骤、**出口门禁（可验证）**、**执行方式**——调研、实现、审核三类操作一律派遣 subagent 执行，主控代理仅负责编排（进度维护、门禁判定、派遣协调、升级用户决策）。
5. **循环机制设计**：为每个修复类循环定义五要素——触发条件 / 动作 / 退出条件 / 最大迭代 / 超限处理（升级用户决策并附问题清单）。
6. **中止条件设计**：明确三类中止情形——(a) 破坏性/不可逆动作需先确认；(b) 循环超限升级用户；(c) DoD 判定失败回退到责任阶段重走；禁止静默放弃。
7. **执行总则与决策链**：门禁制、信息获取决策链（L1 项目内部 → L2 外部 → L3 用户一次性汇总）、单一事实源、状态续传（进度文件）、可验证完成。
8. **注入参考信息与实现要求**：将用户提供的参考路径与实现要求原样收进文档（第八章参考资料 + 第九章实现要求），不增删用户语义。
9. **落盘与汇报**：按 `references/template.md` 章节骨架写入目标路径；向用户汇报：形态、阶段数、任务数、关键门禁与中止机制。

## 五、产出要求

- 路径：`<目标项目根>/docs/prompt/{yyyy-MM-dd}-{loop|graph}-{任务标题}.md`（目录不存在则创建；`{date}` 为任务启动日期，全程不变）；**用户显式指定落盘路径时以用户指定为准**。
- 结构：必须完整包含 `references/template.md` 定义的章节骨架，逐章填写，禁止缺章。
- 信息不可得时的占位符规则：参考信息/项目事实无法获取时（文件不存在、路径无效等），允许使用占位符 `{待调研项}`，**禁止编造**技术细节；占位符须在第八章集中登记，并在需要该信息的节点/阶段设置「回填门禁」——回填未完成不得进入依赖它的步骤。
- 语言：中文；所有门禁、DoD、验证方式必须具体可验证（"通过"须有检查动作）。
- 风格：参照 `references/example.md`——表格化门禁总表、checkbox 出口门禁、伪代码主控循环、编号红线清单。

## 六、反模式（禁止）

- ❌ 定项模式把一份 spec 拆成多个任务 / 重新设计任务 → 一份 spec = 一个任务，只编列不重设计
- ❌ 需求模式过度拆分（单接口、单页面即拆一任务）→ 按模块化内聚拆分，不过度拆分
- ❌ 文档缺中止条件 / 最大迭代 / 升级路径 → 不合格
- ❌ 出口门禁不可验证（"差不多就行"）→ 不合格
- ❌ 调研/实现/审核未设计为 subagent 派遣执行 → 不合格（见模板第四章）
- ❌ 用户已给的信息重复询问 → 直接使用
- ❌ 产物只存在于对话、不落盘 → 必须写文件并提交
