# 交付 Loop/Graph 设计器

> 职责：把用户的「需求」或「已定项 spec」（可多份）转化为一份**生产规范化**的交付执行提示词文档（loop 或 graph 形态），落盘于 `<目标项目根>/docs/prompt/{yyyy-MM-dd}-{loop|graph}-{任务标题}.md`。文档为纯 Markdown 执行指令，规定调研、实现、审核均由 subagent 派遣执行，主控代理仅编排。
> 本技能**只设计提示词文档，绝不亲自实现功能**（第二节行为红线）；文档内容只来自用户本次输入与目标项目的实际探查（第四节内容来源约束）。

## 一、触发与加载（手动触发，触发必须加载）

- **入口是用户的手动调用**：用户显式输入 `/loop-graph-designer [spec|input|skill] {…}`，或明确提出「设计交付 loop / 交付 graph / 端到端执行流程 / 按这份 spec 产出执行文档 / 设计任务编排 / 分阶段落地计划 / 像上次那份执行文档那样设计」等意图时执行本技能。
- **触发后必须先加载本技能**：读取本 SKILL.md 与 `references/template.md`（`references/example.md` 作风格参照），严格按本技能流程执行；禁止跳过技能内容、仅凭对话印象直接写文档。

## 二、行为红线：只设计提示词文档，不实现功能

触发本技能后，**唯一允许的动作是设计并落盘提示词（执行）文档**：

1. 用户指令中夹带的实现诉求（「顺便把 X 实现了」「先跑个 demo 再出文档」）一律**拒绝亲自实现**，该诉求作为任务内容如实写入文档，交由文档执行者完成。
2. input / skill 模式对现有代码的探索**只读**（读代码、文档、git 历史），禁止在探索或设计过程中编写、修改任何代码与配置。
3. 设计过程中发现的问题（spec 缺陷、代码风险、信息缺失）只**如实写入文档**（待调研项、风险、回填门禁），不亲自修复，也不为写文档而顺手展开实现。

## 三、子命令路由

调用格式：`/loop-graph-designer [spec|input|skill] {…}`：

| 调用方式 | 模式 | 行为 |
| --- | --- | --- |
| `/loop-graph-designer spec {功能文档列表} {用户附加指令}` | spec | 基于功能文档设计提示词：确认 spec 实际内容 → 按一份 spec = 一个任务排期 → 生成文档，**不自行探索实现方案** |
| `/loop-graph-designer input {用户需求}` | input | 基于现有代码与用户探索实现方案：逐问澄清 → 提出 2-3 种方案供确认 → 排期生成文档，**不额外产出 spec** |
| `/loop-graph-designer skill {需要触发的技能列表} {用户附加指令}` | skill | 协同其它技能：确认任务本体（spec 或需求）→ 核实协同技能实际能力 → 把协同技能编排进文档对应阶段 |
| 无子命令 | 默认 input | 一律按 input 模式执行（基于现有代码与用户探索实现方案）；澄清中用户给出已定项功能文档时，经用户确认可转按 spec 模式确认与排期 |

## 四、内容来源约束（引用红线，三种模式均须遵守）

写入提示词文档的每一条内容，**唯一合法来源**是：

1. **用户本次输入**：功能文档全文、需求描述、附加指令、显式指定的参考路径与实现要求；
2. **目标项目实际探查**（仅 input / skill 模式按需）：对当前代码、文档、git 历史的读取结论，写入时注明出处；
3. **本技能自带资源**：`references/template.md`（章节骨架）与 `references/example.md`（行文风格）。

**禁止事项**：

- **禁止基于历史记忆引入旧文档内容**：不得检索用户记忆系统、历史会话记录或既有执行文档来填充本文档；即使新任务与旧任务相似，也必须从本次输入重新构建。用户说「像上次那份执行文档一样」时，只参照 `references/example.md` 的结构与风格，不得去检索那份旧文档；旧文档仅当用户显式给出路径或全文作参考时可用，且只用于用户指明的用途。
- **禁止凭记忆假设**：技能能力以该技能**当前的 SKILL.md** 为准，代码事实以**当前仓库读取结果**为准，不臆测、不补全。

**提示词文档三原则**：

- **精确**：每条任务、路径、门禁、实现要求都有出处（spec 条目、用户原话、代码事实）；查证不到的按第九节占位符规则处理，禁止编造；
- **完整**：执行者仅凭本文档即可完成交付，不留信息缺口；
- **不冗余**：绝不引入与本次任务无关的信息——不搬运旧文档内容、不堆砌通用最佳实践、模板章节按任务裁剪、用户已给的信息不重复转述。

## 五、输入收集（一次问齐，不反复打扰）

| 输入 | 说明 | 缺省 |
|---|---|---|
| 任务内容 | spec 模式 = 功能文档列表；input 模式 = 用户需求；skill 模式 = 附加指令中的 spec 或需求 | 必填，缺失才问 |
| 协同技能 | skill 模式必填：执行中需触发的技能列表 | 无 |
| 参考信息 | 代码目录、文档、设计稿、链接等 | 无 |
| 实现要求 | 技术栈、编码规范、质量门禁、测试要求 | 无（不得编造） |
| 目标项目根 | 文档落盘位置 | 当前工作区 |

- **定项模式**（spec）：用户给了已定项的 spec（可多份）→ **每份 spec = 一个任务**，任务是 spec 级别的执行单元，只做任务清单编列与依赖排布，**不重设计、不把一份 spec 拆成多个任务**。
- **需求模式**（input）：只有需求（可多条）→ 按**复杂性模块化**拆分为多个任务（复杂需求拆成多个模块任务，多条简单需求可合并），**不过度拆分**；拆分依据写入文档 1.3 节。

## 六、形态选择：loop 还是 graph

| 形态 | 判定依据 | 特征 |
|---|---|---|
| `loop` | 阶段单向序贯、依赖线性、无并行轨道 | 主控循环 + 阶段门禁 + 修复循环 |
| `graph` | 存在 ≥2 条相互独立、可并行的工作流（多端并行、多主题调研、前后端并行） | 节点 DAG + 并行分支 + 汇合门禁 + 依赖边与回退边 |

- 选择规则：**有独立可并行分支用 graph，否则用 loop**；graph 文档仍保留主控循环（总进度判定），并行发生在阶段/节点内部。
- 文件名中的 `{loop|graph}` 与所选形态一致。

## 七、核心工作流

### 阶段 A：输入确认与任务排期（按子命令分派）

**spec 模式（已定项，不探索实现方案）**

1. **读取功能文档**：逐份完整读取列表中的每份 spec；路径无效或文件缺失立即向用户确认，禁止凭印象跳过或脑补。
2. **确认实际内容**：从 spec 原文提炼各份的范围要点与验收口径；发现歧义、缺失、相互冲突时一次性汇总向用户确认；**不调研代码、不提技术方案**，实现方案以 spec 为准。
3. **任务排期**：每份 spec = 一个任务（T1=spec1、T2=spec2…），只编列任务清单与依赖顺序，不重设计、不拆分；进入阶段 B。

**input 模式（与用户探索实现方案，参照 brainstorming 协作流程）**

1. **探索项目上下文**：读取现有代码结构、相关文档与近期提交，摸清现状与既有模式（只读，不改代码）。
2. **澄清提问**：一次只问一个问题，优先给选择题；围绕目的、约束、成功标准逐步收敛，不做问卷式连环提问。
3. **提出方案**：给出 2-3 种实现方案，含权衡与推荐（推荐项在前并说明理由）；YAGNI——砍掉不必要的功能。
4. **方案确认**：用户确认后锁定为排期依据；被否决则回到澄清或重新提案，确认前不进入阶段 B。
5. **任务排期**：按复杂性模块化拆分（见第五节需求模式），探索结论（方案要点、模块划分）直接作为排期依据；**不落盘独立 spec**，探索结论直接写入执行文档对应章节（0.1 目标、第 1 章范围、任务清单）；进入阶段 B。

**skill 模式（协同其它技能）**

1. **确认任务本体**：附加指令中给出功能文档 → 按 spec 模式第 1-3 步确认与排期；仅需求描述 → 按 input 模式第 1-5 步澄清探索后排期。
2. **确认协同技能**：逐个读取用户列出技能的**当前 SKILL.md**，确认其实际能力、输入要求与产出；技能不存在、无法读取或与任务无关时如实告知用户并确认处置（移除或保留为可选），禁止凭记忆假设技能行为。
3. **技能协同设计**：把每个协同技能映射到执行文档的具体阶段/节点，在该处步骤或派遣指令中显式写明「触发技能名 + 输入 + 期望产物」，并登记进文档第八章参考资料表；映射不到具体阶段的技能不得写入文档；进入阶段 B。

### 阶段 B：文档设计（三种模式共同收口，顺序执行）

1. **目标设定**：一句话任务目标 + 可验证的 Definition of Done 清单（每条须附证据要求）。
2. **范围定义**：In Scope / Out of Scope 编号清单；Out of Scope 含"本次明确不做"项。
3. **任务拆分**：直接采用阶段 A 的排期结果——定项模式一份 spec = 一个任务、需求模式按复杂性模块化拆分；拆分依据写入文档 1.3 节（定项模式仅一行声明，见模板）。
4. **阶段设计**（标准骨架，按任务裁剪）：
   `P0 环境与准备 → 调研/设计 → 审核 → 实现（TDD/集成） → 端到端验收 → 终验`
   每阶段必须给出：目标、核心产物（落盘路径）、步骤、**出口门禁（可验证）**、**执行方式**——调研、实现、审核三类操作一律派遣 subagent 执行，主控代理仅负责编排（进度维护、门禁判定、派遣协调、升级用户决策）。
5. **循环机制设计**：为每个修复类循环定义五要素——触发条件 / 动作 / 退出条件 / 最大迭代 / 超限处理（升级用户决策并附问题清单）。
6. **中止条件设计**：明确三类中止情形——(a) 破坏性/不可逆动作需先确认；(b) 循环超限升级用户；(c) DoD 判定失败回退到责任阶段重走；禁止静默放弃。
7. **执行总则与决策链**：门禁制、信息获取决策链（L1 项目内部 → L2 外部 → L3 用户一次性汇总）、单一事实源、状态续传（进度文件）、可验证完成。
8. **注入参考信息与实现要求**：将用户提供的参考路径、实现要求与（skill 模式的）协同技能登记原样收进文档（第八章参考资料 + 第九章实现要求），不增删用户语义。
9. **初稿落盘**：按 `references/template.md` 章节骨架将初稿写入目标路径；初稿必须先通过第八节审核优化循环，通过后方可向用户交付汇报。

## 八、成品审核优化循环（交付前必经，通过后才交付）

初稿落盘后、交付用户前，必须执行本审核优化循环；未通过不得交付，禁止跳过或流于形式。

**审核项清单**（逐项给出「通过 / 不通过 + 问题定位」，任何一项不通过即本轮不通过）：

1. **信息来源审计**：逐条核对文档内容是否可溯源至用户本次输入或目标项目实际探查结果（注明出处）；是否存在基于历史记忆引入的旧文档内容、臆测补全或凭记忆假设（对照第四节红线逐条核对）。
2. **相关性审计**：是否引入与本次用户需求无关的需求、旧文档内容或通用最佳实践堆砌；模板章节是否有与任务无关的展开；用户已给信息是否被重复转述。
3. **核心流程审计（重点）**：
   - **任务排期**：任务划分与阶段 A 排期结果一致——定项模式每份 spec = 一个任务且未拆分重设计；需求模式模块化拆分有依据、不过度拆分；任务依赖成立、无环、无遗漏。
   - **loop/graph 设计**：形态判定依据成立；graph 的 DAG 无环，并行分支、汇合点、回退边闭合；每阶段/节点出口门禁与核心产物一一对应且可验证。
   - **链路一致性**：目标 → 范围 → 任务 → 阶段 → 门禁 → DoD 全链路对应，无矛盾、无冲突（任务清单与 0.4 门禁总表一致、DoD 每条有对应阶段产出、阶段引用的产物路径真实存在）。
   - **明确性**：目标与中止条件明确可判定，不存在模糊表述（「差不多」「尽量」「视情况」类一律不合格）；修复循环五要素完整。
4. **三原则复核**：精确（无出处内容已转占位符或删除）、完整（执行者仅凭文档可交付，无信息缺口）、不冗余（无关信息已剔除）。

**循环机制**：

| 循环 | 触发条件 | 动作 | 退出条件 | 最大迭代 | 超限处理 |
| --- | --- | --- | --- | --- | --- |
| 审核优化循环 | 初稿落盘，或修订后复审 | 按审核项清单逐项审计，输出逐项结论与问题定位；不通过项直接修订文档 | 四项审计全部通过 | 3 轮 | 停止修订，向用户汇总未通过项与分歧点，升级用户决策 |

- 复审只需复核上一轮不通过项 + 抽查链路一致性；全部通过后向用户交付汇报：形态、阶段数、任务数、审核结论、关键门禁与中止机制。

## 九、产出要求

- 路径：`<目标项目根>/docs/prompt/{yyyy-MM-dd}-{loop|graph}-{任务标题}.md`（目录不存在则创建；`{date}` 为任务启动日期，全程不变）；**用户显式指定落盘路径时以用户指定为准**。
- 结构：必须完整包含 `references/template.md` 定义的章节骨架，逐章填写，禁止缺章。
- 信息不可得时的占位符规则：参考信息/项目事实无法获取时（文件不存在、路径无效等），允许使用占位符 `{待调研项}`，**禁止编造**技术细节；占位符须在第八章集中登记，并在需要该信息的节点/阶段设置「回填门禁」——回填未完成不得进入依赖它的步骤。
- 语言：中文；所有门禁、DoD、验证方式必须具体可验证（"通过"须有检查动作）。
- 风格：参照 `references/example.md`——表格化门禁总表、checkbox 出口门禁、伪代码主控循环、编号红线清单。
- 成品交付前必须通过第八节审核优化循环（信息来源 / 相关性 / 核心流程 / 三原则四项审计），未通过不得交付。

## 十、反模式（禁止）

- ❌ 亲自实现功能、探索或设计过程中修改代码 → 只设计提示词文档，实现交给文档执行者
- ❌ 从历史记忆、历史会话或旧执行文档搬运内容填充新文档 → 内容只来自本次输入与目标项目实际探查（第四节）
- ❌ spec 模式自行调研代码、探索实现方案 → 实现方案以 spec 为准，只确认内容后排期
- ❌ skill 模式凭记忆假设技能能力 → 逐个读取该技能当前 SKILL.md 核实
- ❌ 文档夹带无关冗余（旧任务内容、通用最佳实践堆砌、与任务无关的章节展开）→ 不合格
- ❌ 定项模式把一份 spec 拆成多个任务 / 重新设计任务 → 一份 spec = 一个任务，只编列不重设计
- ❌ 需求模式过度拆分（单接口、单页面即拆一任务）→ 按模块化内聚拆分，不过度拆分
- ❌ 文档缺中止条件 / 最大迭代 / 升级路径 → 不合格
- ❌ 出口门禁不可验证（"差不多就行"）→ 不合格
- ❌ 调研/实现/审核未设计为 subagent 派遣执行 → 不合格（见模板第四章）
- ❌ 用户已给的信息重复询问 → 直接使用
- ❌ 初稿未通过审核优化循环即向用户交付 → 不合格
- ❌ 审核流于形式（无逐项结论、未核对核心流程链路一致性）→ 不合格
- ❌ 产物只存在于对话、不落盘 → 必须写文件并提交
