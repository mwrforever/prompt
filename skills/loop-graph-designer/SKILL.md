# 交付 Loop/Graph 设计器

> 职责：把用户的「需求」或「已定项 spec」（可多份）转化为一份生产规范化的交付执行提示词文档（loop 或 graph 形态），落盘于 `<目标项目根>/docs/prompt/{yyyy-MM-dd}-{loop|graph}-{任务标题}.md`。文档为纯 Markdown 执行指令：调研、实现、审核均由执行者派遣 subagent 完成，主控代理仅编排。
> 边界：本技能只设计文档、绝不实现功能（第二节）；文档内容只来自用户本次输入与目标项目实际探查（第三节）。

## 一、触发与路由

- **触发**：用户显式调用 `/loop-graph-designer [spec|input|skill|example] {…}`，或明确提出「设计交付 loop / 交付 graph / 端到端执行流程 / 按这份 spec 产出执行文档 / 设计任务编排 / 分阶段落地计划 / 按风险扫描等场景生成执行文档 / 像上次那份执行文档那样设计」等意图。
- **加载**：触发后必须先读本 SKILL.md 与 `references/template.md`（`references/example.md` 作风格参照；example 模式另读 `examples/README.md` 场景索引与对应场景文件），严格按流程执行；禁止跳过技能内容、仅凭对话印象直接写文档。

| 调用方式 | 模式 | 行为 |
| --- | --- | --- |
| `spec {功能文档列表} {附加指令}` | spec | 基于已定项 spec 设计：确认实际内容 → 排期 → 出文档，**不探索实现方案** |
| `input {用户需求}` | input | 基于现有代码与用户共同探索方案：澄清 → 提案 → 排期 → 出文档，**不额外产出 spec** |
| `skill {技能列表} {附加指令}` | skill | 协同其它技能：确认任务本体（spec 或需求）→ 核实技能实际能力 → 编排进文档对应阶段 |
| `example {场景} {用户指令}` | example | 场景化专项：按 `examples/` 场景索引（`examples/README.md`）与对应场景示例生成该场景执行文档；场景未收录时结束并按列表降级选择；当前仅内置 `risk`（项目风险扫描） |
| 无子命令 | 默认 input | 按 input 模式执行；澄清中用户给出已定项功能文档时，经用户确认可转 spec 模式 |

## 二、行为红线：只设计文档，不实现功能

触发后唯一允许的动作是设计并落盘提示词文档：

1. 指令中夹带的实现诉求（「顺便把 X 实现了」「先跑个 demo 再出文档」）一律拒绝亲自实现，作为任务内容如实写入文档，交由文档执行者完成。
2. 对现有代码的探索只读（读代码、文档、git 历史）；探索与设计过程中不编写、不修改任何代码与配置。
3. 发现的问题（spec 缺陷、代码风险、信息缺失）只写入文档（待调研项、风险、回填门禁），不亲自修复，也不为写文档顺手展开实现。

## 三、内容来源与三原则

文档中每条内容的唯一合法来源：

1. **用户本次输入**：spec 全文、需求描述、附加指令、显式指定的参考路径与实现要求；
2. **目标项目实际探查**（仅 input / skill 模式按需）：对当前代码、文档、git 历史的读取结论，写入时注明出处；
3. **本技能自带资源**：`references/template.md`（章节骨架）、`references/example.md`（行文风格）、example 模式的场景索引与专项示例 `examples/`（`README.md` 索引，每场景一个独立文件；当前仅 `risk.md`：项目风险扫描）。

- **禁止引用历史记忆**：不检索用户记忆系统、历史会话或既有执行文档来填充内容；新旧任务再相似也必须从本次输入重建。用户说「像上次那份执行文档一样」时，只参照 `example.md` 的结构与风格，不检索那份旧文档；旧文档仅当用户显式给出路径或全文时，按指明用途使用。
- **禁止凭记忆假设**：技能能力以该技能当前 SKILL.md 为准，代码事实以当前仓库读取结果为准，不臆测、不补全。
- **场景示例只借结构与做法**：场景示例是上一真实任务的产出，其中的项目特定事实（路径、端口、命令、宪法文件、产物与分支约定等）禁止照搬进新文档；生成时逐项替换为目标项目实际探查结果，替换不到的按占位符规则处理。

**三原则**（交付前按第五节逐项复核）：

- **精确**：每条任务、路径、门禁、实现要求都有出处（spec 条目、用户原话、代码事实）；查证不到的按第六节占位符规则处理，禁止编造；不参杂「视情况 / 尽量 / 可能」类不确定性描述；
- **完整**：执行者仅凭本文档即可完成交付，不留信息缺口；
- **不冗余**：一句话能讲清目标的绝不长篇大论；不搬运旧文档内容、不堆砌通用最佳实践、模板章节按任务裁剪、用户已给的信息不重复转述、不科普协同技能原理（只一句带过）。

**成品格式约束**（精简性的硬边界，逐项审计）：

- 全文不超过 5000 字：超限先砍描述性冗余与重复信息，禁止砍门禁与机制完整性；
- 层级不超过三层：标题仅 `#` 文档题 → `##` 章 → `###` 节/阶段三级，禁用 `####`，列表嵌套不超过一层；
- 表格不超过 3 张：0.3 门禁总表、WBS 任务清单、循环汇总表（graph 依赖图用代码块，不计）；其余信息一律精简列表或一句话。

## 四、核心工作流

### 阶段 A：输入确认与任务排期

共用输入项（缺失才问，一次问齐，不反复打扰）：

| 输入 | 说明 | 缺省 |
|---|---|---|
| 任务内容 | spec 列表（spec 模式）/ 需求描述（input 模式）/ 附加指令中的本体（skill 模式） | 必填 |
| 协同技能 | 执行中需触发的技能列表 | 仅 skill 模式必填 |
| 参考信息 | 代码目录、文档、设计稿、链接等 | 无 |
| 实现要求 | 技术栈、编码规范、质量门禁、测试要求 | 无（不得编造） |
| 目标项目根 | 文档落盘位置 | 当前工作区 |

任务粒度原则（排期唯一依据，依据写入文档 1.3 节）：**定项模式一份 spec = 一个任务**，只编列任务清单与依赖顺序，不拆分、不重设计；**需求模式按复杂性模块化拆分**——复杂需求拆成模块任务、多条简单需求可合并，单任务可独立交付且不过度拆分。无论何种模式，每项任务都必须带明确目标——做什么、产出什么、如何验收，禁止「协助完成」「相关梳理」类泛化描述；目标写不清的任务不得进入排期。

**spec 模式**

1. 逐份完整读取 spec；路径无效或文件缺失立即向用户确认，禁止凭印象跳过或脑补。
2. 从原文提炼各份范围要点与验收口径；歧义、缺失、相互冲突一次性汇总确认；不调研代码、不提技术方案，实现方案以 spec 为准。
3. 每份 spec = 一个任务（T1=spec1、T2=spec2…），编列清单与依赖后进入阶段 B。

**input 模式**（参照 brainstorming 协作流程）

1. 只读探索项目现状：代码结构、相关文档、近期提交，摸清既有模式。
2. 澄清提问：一次只问一个，优先选择题，围绕目的、约束、成功标准逐步收敛，不做问卷式连环提问。
3. 提出 2-3 种实现方案，含权衡与推荐（推荐在前并说明理由）；YAGNI，砍掉不必要功能。
4. 用户确认后锁定为排期依据；被否决则回到澄清或重新提案，确认前不进入阶段 B。
5. 按模块化拆分排期；探索结论（方案要点、模块划分）直接写入执行文档（0.1 目标、第 1 章范围、任务清单），不落盘独立 spec。

**skill 模式**

1. 确认任务本体：附加指令给出功能文档 → 走 spec 模式步骤；仅需求描述 → 走 input 模式步骤。
2. 逐个读取协同技能的当前 SKILL.md，核实实际能力、输入要求与产出；技能不存在、无法读取或与任务无关时如实告知用户并确认处置（移除或降为可选），禁止凭记忆假设。
3. 技能协同设计：把每个协同技能映射到文档具体阶段/节点，在该处步骤或派遣指令中一句带过「触发技能名 + 输入 + 期望产物」（不展开该技能的内部流程与原理），并登记进文档第八章；映射不到具体阶段的技能不写入。进入阶段 B。

**example 模式**（场景化专项文档）

场景专项示例独立维护于 `examples/` 目录（每场景一个独立文件），场景索引、使用流程与场景未收录时的降级规则统一见 `examples/README.md`；触发后先读该索引，再按所选场景执行，任务与派遣同样遵守目标明确约束，经阶段 B 与第五节审核循环后方可交付。

### 形态判定（排期后、文档设计前）

| 形态 | 判定依据 | 特征 |
|---|---|---|
| `loop` | 阶段单向序贯、依赖线性、无并行轨道 | 主控循环 + 阶段门禁 + 修复循环 |
| `graph` | 存在 ≥2 条相互独立、可并行的工作流（多端并行、多主题调研、前后端并行） | 节点 DAG + 并行分支 + 汇合门禁 + 依赖边与回退边 |

有独立可并行分支用 graph，否则用 loop；graph 文档仍保留主控循环（总进度判定），并行发生在阶段/节点内部。文件名中的 `{loop|graph}` 与判定结果一致。

### 阶段 B：文档设计（各模式共同收口，顺序执行）

1. **目标**：一句话任务目标 + 可验证的 Definition of Done 清单，每条附证据要求。
2. **范围**：In Scope / Out of Scope 编号清单，Out of Scope 含「本次明确不做」项。
3. **任务拆分**：直接采用阶段 A 排期结果，拆分依据写入 1.3 节（定项模式仅一行声明，见模板）；每项任务带明确目标（做什么、产出什么、如何验收），禁止泛化描述。
4. **阶段设计**（标准骨架按任务裁剪）：`P0 环境与准备 → 调研/设计 → 审核 → 实现（TDD/集成） → 端到端验收 → 终验`；每阶段给出步骤、核心产物（落盘路径）、可验证出口门禁；调研/实现/审核三类操作一律派遣 subagent，主控代理仅编排（进度维护、门禁判定、派遣协调、升级用户决策），制度细节由模板第四章承载。
5. **主控循环**：0.2 伪代码必须基于本任务逐阶段展开，禁止通用抽象循环——初始化行写真实初始化动作（基线/版本确认、进度文件创建等）；每阶段落名并附本任务出口门禁摘要与关键动作（派遣对象、协同技能、引用的文档章节）；任务的真实迭代单元（批次/专项/条目清单）写入循环体；分支三态写具体去向（进度记 complete / 回退目标阶段 / 重审内容）。写法见模板 0.2 与 `references/example.md` 示例一。
6. **循环机制**：为每个修复类循环定义五要素——触发条件 / 动作 / 退出条件 / 最大迭代 / 超限处理（升级用户并附问题清单）。
7. **中止条件**：(a) 破坏性/不可逆动作先确认；(b) 循环超限升级用户；(c) DoD 判定失败回退责任阶段重走；禁止静默放弃。
8. **执行总则与决策链**：门禁制、信息获取决策链（L1 项目内部 → L2 外部 → L3 用户一次性汇总）、单一事实源、状态续传（进度文件）、可验证完成。
9. **注入用户信息**：参考路径、实现要求与协同技能登记原样收入文档第八章，不增删用户语义。
10. **落盘**：按 `references/template.md` 章节骨架写入目标路径；初稿先对照第三节成品格式约束自查（≤5000 字、层级三级、表格 ≤3 张），再进入第五节审核优化循环，通过后方可向用户交付。

## 五、审核优化循环（交付前必经）

初稿落盘后、交付用户前逐项审计，输出「通过 / 不通过 + 问题定位」；任何一项不通过即修订并复审，禁止跳过或流于形式。

1. **信息来源审计**：逐条内容可溯源至用户本次输入或目标项目实际探查（注明出处）；无历史记忆引入、臆测补全、凭记忆假设（对照第三节红线）。
2. **相关性审计**：无与本次需求无关的内容——旧文档搬运、通用最佳实践堆砌、与任务无关的章节展开、用户已给信息的重复转述。
3. **核心流程审计**（重点）：
   - **任务排期**：与阶段 A 结果一致——定项模式每份 spec = 一个任务且未拆分重设计；需求模式拆分有据、不过度；任务依赖成立、无环、无遗漏。
   - **loop/graph 设计**：形态判定依据成立；graph 的 DAG 无环，并行分支、汇合点、回退边闭合；每阶段/节点出口门禁与核心产物一一对应且可验证；主控循环任务化——逐阶段落名、门禁摘要与迭代单元取自本任务、分支去向具体，无「定位阶段→执行→校验」式通用抽象循环。
   - **流程关系反思**（逐节点逐边推演，不止看结构闭合）：
     - 并行反思：并行的任务/派遣逐对核对——是否存在写同一文件、同一资源、共享状态类严重冲突；是否存在漏判的明显依赖（上游产出是下游输入却被判并行）；存疑即改串行并同步更新并行性判定；
     - 节点与边：逐节点审核流向——输入来自哪个上游产物、产出供哪个下游消费、衔接是否成立；条件边与回退边的触发条件正确且完备（每个条件有归宿，无不可达节点与死分支）；每条边的指向合理且必要，可合并或可删除的边不留；
     - 循环收敛：逐个局部循环推演一轮——退出条件可满足、最大迭代与超限处理在，不会死循环；回退边不构成无出口的环；
     - 其它反思：状态续传、升级路径、会话中断恢复等流程关系上的其它隐患。
   - **链路一致性**：目标 → 范围 → 任务 → 阶段 → 门禁 → DoD 全链路对应无矛盾（主控循环与 0.3 门禁总表逐行对应、任务清单与 0.3 门禁总表一致、DoD 每条有对应阶段产出、引用的产物路径真实存在）。
   - **明确性**：目标与中止条件明确可判定，无「差不多」「尽量」「视情况」类模糊表述；修复循环五要素完整。
4. **精简性与可读性审计**：一句话能讲清的不展开——无重复转述、无原理科普（协同技能全文档只一句带过，不展开其内部流程与原理）、无过程性流水账；格式红线达标：全文 ≤5000 字、标题三级（禁 `####`）且列表嵌套 ≤1 层、表格 ≤3 张（门禁总表 / WBS / 循环汇总）。
5. **三原则复核**：精确（无出处内容已转占位符或删除、无不确定性表述）、完整（执行者仅凭文档可交付）、不冗余（无关信息已剔除）。

| 循环 | 触发条件 | 动作 | 退出条件 | 最大迭代 | 超限处理 |
| --- | --- | --- | --- | --- | --- |
| 审核优化循环 | 初稿落盘，或修订后复审 | 逐项审计；不通过项直接修订文档 | 五项审计全部通过 | 3 轮 | 停止修订，向用户汇总未通过项与分歧点，升级用户决策 |

复审只复核上一轮不通过项 + 抽查链路一致性；全部通过后向用户交付汇报：形态、阶段数、任务数、成品字数、审核结论、关键门禁与中止机制。

## 六、产出要求

- **路径**：`<目标项目根>/docs/prompt/{yyyy-MM-dd}-{loop|graph}-{任务标题}.md`；目录不存在则创建；日期为任务启动日期，全程不变；用户显式指定路径时以用户指定为准。
- **结构**：完整套用 `references/template.md` 章节骨架，逐章填写，禁止缺章，并遵守第三节成品格式约束（≤5000 字、层级三级、表格 ≤3 张）。
- **占位符**：参考信息/项目事实无法获取时（文件不存在、路径无效等），用 `{待调研项}` 占位，禁止编造技术细节；占位符在第八章集中登记，并在依赖它的节点/阶段设「回填门禁」——回填未完成不得进入依赖步骤。
- **语言与风格**：中文；门禁、DoD、验证方式必须具体可验证（「通过」须有检查动作）；风格参照 `references/example.md`——门禁总表单表化（含产物路径）、checkbox 出口门禁、伪代码主控循环、编号红线清单。

## 七、反模式

- ❌ 亲自实现功能，或探索/设计过程中改代码 → 只设计文档（第二节）
- ❌ 从历史记忆、历史会话或旧执行文档搬运内容 → 只用本次输入与实际探查（第三节）
- ❌ spec 模式调研代码、自行探索实现方案 → 实现方案以 spec 为准
- ❌ skill 模式凭记忆假设技能能力 → 逐个读取该技能当前 SKILL.md 核实
- ❌ 一份 spec 拆成多个任务重新设计 / 单接口、单页面即拆一任务 → 定项不拆分；需求按模块内聚拆分
- ❌ 文档夹带无关冗余（旧任务内容、最佳实践堆砌、无关章节展开）→ 违反三原则
- ❌ 成品冗长或格式失控（长篇大论、协同技能原理科普、表格 >3 张、层级 >3 层、超 5000 字）→ 第三节成品格式约束 + 第五节精简性与可读性审计
- ❌ 出口门禁不可验证（「差不多就行」）、缺中止条件/最大迭代/升级路径 → 不合格
- ❌ 调研/实现/审核未设计为 subagent 派遣执行 → 不合格（模板第四章）
- ❌ 任务目标泛化（「协助完成」「相关梳理」等不可验收描述）→ 每项任务与每次派遣带明确目标与完成标准（模板 1.3 与第四章）
- ❌ 主控循环写通用抽象模板（「while DoD 未满足: 定位阶段→执行→校验」，不落本任务阶段、门禁与迭代单元）→ 0.2 按本任务逐阶段展开（模板 0.2，风格见 example.md 示例一）
- ❌ 并行、条件边、回退边未经冲突与依赖反思（想当然并行、边指向不成立或冗余）→ 第五节流程关系反思逐节点逐边推演
- ❌ 用户已给的信息重复询问或重复转述 → 直接使用
- ❌ 初稿未过审核循环即交付，或审核无逐项结论、流于形式 → 不合格
- ❌ 产物只存在于对话、不落盘 → 必须写文件并提交
