# 交付执行文档模板（章节骨架）

> 本文件定义 `loop-graph-designer` 生成文档的**必含章节骨架与逐章填写规则**。生成时逐章套用，禁止缺章、禁止改变章节编号结构。方括号 `[...]` 为占位说明，生成时必须替换为具体内容；**信息不可得时允许使用 `{待调研项}` 占位符（禁止编造），但必须在第八章集中登记，并在需要该信息的节点/阶段设置「回填门禁」**；`※` 标注的为规则性说明，不写入最终文档。

## 文档头（生成文档最顶部）

```markdown
# {任务标题} · 交付{loop|graph}执行设计

> 本文档为唯一执行依据。执行者必须按阶段门禁（P0→P{n}）顺序推进，所有循环仅在满足对应退出条件后方可进入下一阶段；**全任务仅在「第五章 DoD」全部满足后才允许退出主循环**。{若目标项目存在 AGENTS.md/CLAUDE.md 等宪法文件：其为本任务最高约束，任何产出与之冲突即判定不合格。}
```

※ 日期、任务标题：`{date}` 使用任务启动日期（yyyy-MM-dd），全程不变更；标题用简短中文或 kebab-case。

---

## 0. 执行框架总览

### 0.1 目标

一句话任务目标 + 完成判定标准（可验证）。

### 0.2 主控循环（Master Loop / Graph）

- loop 形态：伪代码主控循环（初始化进度 → while DoD 未满足: 定位阶段 → 执行 → 校验出口门禁 → 通过推进 / 未通过进入修复循环 / 超限升级用户 → 全部门禁通过 → 终验报告 → 退出）。
- graph 形态：除主控循环外，另给节点依赖图（mermaid / ascii DAG）：节点 = 阶段或并行分支，边 = 依赖关系，标注并行分支、汇合点、回退边。

### 0.3 产物索引

表格：产物 | 路径（全部落盘并提交 git，禁止仅存于对话上下文）。

### 0.4 阶段门禁总表

表格：阶段 | 名称 | 核心产物 | 出口门禁（一句话描述）。

※ graph 形态可在 0.4 后追加 0.5 依赖图。

---

## 1. 任务范围定义

### 1.1 范围内（In Scope）

编号列表，逐项对应任务目标。若为定项模式，逐项引用 spec 中的章节/条目。

### 1.2 范围外（Out of Scope）

编号列表，明确"本次不做"项，防止执行期蔓延。

### 1.3 任务划分与拆分依据（需求模式必含；定项模式一行声明）

- **定项模式**：一行声明"每份 spec = 一个任务，共 N 个任务（T1~Tn），各自验收标准取自对应 spec，不再拆分"，本节其余内容不写。
- **需求模式**：给出功能域分解表（功能域 | 责任 | 并行性判定）与拆分依据：
  - **复杂性模块化**：按业务能力内聚拆分为模块任务（如"用户管理""角色权限""审计日志"各为一任务）；单任务须可独立交付（有自己的验收标准），并可在一次 subagent 派遣周期内完成"调研 → 实现 → 审核"闭环
  - **不过度拆分**：能在一个任务内闭环的不拆；相邻强耦合模块（共享同一数据模型 / 同一页面 / 同一接口族）合并为一个任务
  - 可选依据：依赖先行、风险隔离、并行度最大化（按任务选取并说明理由）
- 任务清单本体（WBS 表）放在第 3 章对应实现节点/阶段节内，本节只给分解逻辑。

---

## 2. 全局执行总则

按需选用以下条目（可增删，为执行器行为约束）：

1. **阶段门禁制**：严格顺序推进，未满足出口门禁禁止进入下一阶段；回退必须记录在进度文件中
2. **信息获取决策链**（严格按优先级，不得跳级）：
   - L1 项目内部：源代码、AGENTS.md/README、已有测试、git 历史
   - L2 外部信息：框架官方文档、行业最佳实践
   - L3 用户决策：L1/L2 仍无法满足时，**一次性汇总全部待决策问题**（含背景、可选项、建议方案）
   - 每次触发 L2/L3 必须在进度文件「决策日志」中记录触发原因与结论
3. **循环收敛**：所有修复类循环设最大迭代次数，超限升级用户，禁止无限循环或静默放弃
4. **单一事实源**：锁定后的 spec（或本文档）为实现唯一依据，实现中发现规格缺陷必须回改 spec 再继续
5. **状态续传**：每完成一个任务或通过一个门禁，立即更新进度文件；会话中断后从进度文件恢复
6. **可验证完成**：任何"完成"声明必须附可验证证据（测试输出、命令结果、文件路径）
7. **subagent 执行制**：调研、实现（执行）、审核三类操作一律派遣 subagent 执行；主控代理（执行本文档的主代理）仅负责编排——进度维护、门禁判定、派遣协调、升级用户决策，禁止亲自执行上述三类操作

---

## 3. 阶段详细定义

逐阶段一节。阶段编号连贯：P0, P1, …, P{n-1}（含终验阶段）。

**loop 形态每节结构：**

```markdown
### P{k} {阶段名称}

**步骤**：

1. {动作1}
2. {动作2}

**核心产物**：{产物路径}

**出口门禁**：

- [ ] {可验证门禁1}
- [ ] {可验证门禁2}
```

**graph 形态每节结构（节点版）：**

```markdown
### N{k} {节点名称}

**依赖节点**：{Nx, Ny 或 "无"（并行起点）}

**输入**：{依赖节点的产物}

**步骤**：

1. {动作1}
2. {动作2}

**核心产物**：{产物路径}

**出口门禁**：

- [ ] {可验证门禁}
- [ ] {可验证门禁}

**回退边**：{门禁不满足时回退到哪个节点重新执行}
```

※ 门禁规则：
- 每条门禁必须可验证——有客观检查方式（命令、测试、文件存在性、审核结论），禁止"差不多"式表述
- 步骤写成「动作 + 验证」对，如 `1. [步骤] → 验证：[检查方式]`
- 标准阶段骨架（按任务裁剪）：P0 环境与准备 → 调研/设计 → 审核 → 实现（TDD/集成） → 端到端验收 → 终验
- 实现类阶段必须包含 RED→GREEN→REFACTOR 循环、lint/typecheck/测试校验、进度记录、Conventional Commits 等落地细则；是否强制 TDD 由用户实现要求决定
- 任务清单（WBS 表）置于对应实现节点/阶段节内（每节一张表：任务ID | 描述 | 依赖 | 涉及端 | 派遣角色 | 验收标准 | 测试要求），0.4 门禁总表与之呼应；任务粒度遵循 1.3——一份 spec = 一个任务，需求按模块化拆分且不过度拆分
- 含 `{待调研项}` 占位符的节点/阶段必须设「回填门禁」：占位符全部回填并记录出处后该门禁才可勾选，未回填不得放行依赖该信息的步骤

---

## 4. 协作与派遣规范（subagent 执行制）

调研、实现（执行）、审核三类操作一律由 subagent 派遣完成，主控代理不亲自执行：

| 派遣角色 | 职责边界 | 派遣时机 |
| --- | --- | --- |
| 调研专员 | 信息采集：L1 项目内部（源码/文档/测试/git 历史）与 L2 外部（官方文档、最佳实践）；输出调研报告 | 阶段/节点入口，或执行中发现信息不足时 |
| 实现专员 | 按 spec/WBS 编写代码与测试、自校验（lint/测试）；输出代码与进度记录 | 对应实现节点启动时 |
| 审核专员 | 对照 spec 审核实现、测试质量、门禁符合性；输出审核报告 | 实现节点出口门禁前；独立于实现专员，禁止自我审核 |

每次派遣必须包含五要素：

```markdown
【角色】调研专员 / 实现专员 / 审核专员（明确单一职责）
【输入】具体文件路径 / 报告路径 / 上下文说明（禁止模糊指代）
【职责】做什么、不做什么（明确边界）
【输出】产物路径 + 必含内容结构
【完成标准】可验证的退出条件

**并行规则**：无依赖的派遣并行执行；有依赖的严格顺序。
```

※ graph 形态在此节补充并行分支的执行说明（哪些节点可同时派遣、汇合点如何同步）；实现节点内，任务可分组按模块派遣多个实现专员并行。

---

## 5. 完成条件（Definition of Done · 退出唯一依据）

checkbox 清单，每条附证据要求。覆盖：

- [ ] 任务范围内 {各项} 全部完成，集成测试通过
- [ ] 所有对接项落地并可端到端跑通（如有）
- [ ] e2e 测试覆盖任务全部功能项及边界问题（空态、非法输入、超长值、未登录/会话过期、权限越界、并发与重复提交、网络异常、分页边界——按任务选用）
- [ ] 测试流程全部通过（单测、集成、e2e）
- [ ] CI 流程全绿（如项目有 CI）
- [ ] 代码审核（review/审核专员）通过
- [ ] 调研、实现、审核全部由 subagent 派遣完成且派遣记录完整（证据：进度文件派遣日志）
- [ ] 全部产物文档已提交 git
- [ ] 终验报告生成且每项附证据

※ 按任务增删条目；每条必须含证据类型。

## 6. 循环与中止机制汇总

```markdown
| 循环 | 触发条件 | 动作 | 退出条件 | 最大迭代 | 超限处理 |
| --- | --- | --- | --- | --- | --- |
| {修复循环1} | {什么情况进入} | {循环内做什么} | {满足什么退出} | {N} | 升级用户（附问题清单与当前状态） |
```

※ 中止条件专节（若任务含破坏性/外部动作），明确写出：
- 需要先向用户确认的动作类型（删除数据、发布对外、不可逆操作等）
- 循环超限升级用户的时机与格式（问题清单 + 建议方案）
- 静默放弃、伪造证据、跳过门禁为禁止行为（并入第七章红线）

---

## 7. 红线禁止事项

编号列表（按任务调整，通常含）：

1. 禁止跳过任何阶段门禁，或在出口条件未满足时推进下一阶段
2. 禁止未经测试验证即标记任务或阶段完成
3. 禁止在锁定后偏离 spec 实现（发现规格问题必须先回改 spec）
4. 禁止绕过审核直接合入代码
5. 禁止缩小任务范围、削减功能项或边界测试以换取"完成"
6. 禁止伪造、跳过或选择性运行测试与 CI
7. 禁止在 L1/L2 可调研的情况下直接询问用户
8. 禁止丢弃或重做已完成且有进度记录的阶段
9. 禁止产物仅存于对话上下文而不落盘提交

---

## 8. 参考资料（可选，用户提供时必含）

用户提供的参考信息原样收录：

```markdown
| 参考 | 路径/链接 | 用途 |
| --- | --- | --- |
| {名称} | {路径} | {在哪个阶段使用} |
```

※ skill 协同模式：用户指定协同技能时，每个技能必须映射到具体阶段/节点，在该处步骤或派遣指令中显式写明「触发技能名 + 输入 + 期望产物」，并登记进本章参考资料表（参考=技能名、路径=该技能 SKILL.md 位置、用途=触发阶段与产出）；协同技能的实际能力以该技能当前 SKILL.md 为准，未能映射到具体阶段的技能不得写入文档。

## 9. 实现要求与约束（可选，用户提供时必含）

用户提供的实现要求原样收录（技术栈、编码规范、测试覆盖要求、CI 要求、语言要求等），并声明"与本任务最高约束文件冲突时以约束文件为准"。

※ 若实现要求含覆盖率分级（如核心 X% / 非核心 Y%），文档必须锁定「核心功能清单」的界定方式与锁定时机：在首个实现节点出口门禁前确定清单（可引用既有宪法条款界定，如涉及资金/认证/权限/一致性/对外 API 的路径），清单随 spec 一并落盘，覆盖率门禁以该清单核对。

※ 用户未提供参考信息/实现要求时，第八、九章省略，但门禁与 DoD 中不得出现凭空编造的技术要求。
