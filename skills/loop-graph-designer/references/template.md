# 交付执行文档模板（章节骨架）

> 本文件定义生成文档的**必含章节骨架与逐章填写规则**：逐章套用，禁止缺章、禁止改变章节编号结构。
> **成品格式红线**（精简性，交付前逐项审计）：全文不超过 5000 字；标题仅三级（`#` 文档题 → `##` 章 → `###` 节/阶段，禁用 `####`），列表嵌套不超过一层；全文表格不超过 3 张（0.3 门禁总表、3 章 WBS 任务清单、6 章循环汇总表），其余信息一律精简列表或一句话；一句话能讲清的绝不长篇大论，协同技能只一句带过、不展开原理。
> 方括号 `[...]` 为占位说明，生成时替换为具体内容；信息不可得时允许 `{待调研项}` 占位（禁止编造），登记进第八章并在依赖它的节点/阶段设「回填门禁」。
> `※` 标注为规则性说明，不写入最终文档。

## 文档头（生成文档最顶部）

```markdown
# {任务标题} · 交付{loop|graph}执行设计

> 本文档为唯一执行依据。执行者必须按阶段门禁（P0→P{n}）顺序推进，所有循环仅在满足对应退出条件后方可进入下一阶段；**全任务仅在「第五章 DoD」全部满足后才允许退出主循环**。
```

※ 日期用任务启动日期（yyyy-MM-dd），全程不变；标题用简短中文或 kebab-case。目标项目存在 AGENTS.md/CLAUDE.md 等宪法文件时，在文档头追加一句：「{宪法文件} 为本任务最高约束，任何产出与之冲突即判定不合格。」

---

## 0. 执行框架总览

### 0.1 目标

一句话任务目标 + 一句话可验证完成判定，不展开背景。

### 0.2 主控循环（Master Loop / Graph）

- loop 形态：伪代码主控循环**按本任务逐阶段展开**，禁止写「定位阶段 → 执行 → 校验」的通用抽象循环：
  - 初始化行写本任务真实初始化动作（基线/版本确认、进度文件创建、需先读的注意事项等）；
  - 每阶段一行或一段：`P{k} {本任务阶段名}（{关键动作：派遣对象 / 协同技能 / 产出}）→ {本任务出口门禁摘要}`，与 0.3 门禁总表逐行对应；
  - 任务的真实迭代单元（批次 / 专项 / 条目清单）落进循环体，含批次级审核与分支三态：`while {存在未完成批次}: {批内动作} → {批次级审核} ├─ 通过 → 进度文件记 complete，进入下一批 ├─ 不通过 → {修复循环（≤N 轮，见第六章）} └─ 超限 → 升级用户（附问题清单与当前状态）`；
  - 阶段内多分支（如审核不通过、合入冲突消解）直接写出本任务的具体去向，可引用本文档其他节；
  - 尾行：终验阶段（终验报告 + DoD 逐项勾选附证据）→ DoD 全满足退出，未满足回退责任阶段重走（见第六章终验循环）。
- graph 形态：主控循环同样逐节点落名展开，并在其后给节点依赖图（mermaid / ascii DAG）：节点 = 阶段或并行分支，边 = 依赖关系；标注并行分支、汇合点、回退边。

### 0.3 阶段门禁总表

表格：阶段 | 名称 | 核心产物（含落盘路径） | 出口门禁（一句话）。产物落盘路径只在此表登记，不另设产物索引节。

---

## 1. 任务范围定义

### 1.1 范围内（In Scope）

编号列表，逐项对应任务目标；定项模式逐项引用 spec 章节/条目。

### 1.2 范围外（Out of Scope）

编号列表，明确「本次不做」项。

### 1.3 任务划分与拆分依据（需求模式必含；定项模式一行声明）

- **定项模式**：一行声明——「每份 spec = 一个任务，共 N 个任务（T1~Tn），验收标准取自对应 spec，不再拆分」，其余不写。
- **需求模式**：拆分依据 3~5 条——每项任务一句可验证目标（做什么、产出什么、如何验收）；按业务内聚拆模块，单任务可独立交付且一次派遣周期可闭环；不过度拆分（强耦合模块合并）；可选依据：依赖先行、风险隔离、并行度最大化。
- WBS 任务清单本体放第 3 章实现阶段节内（全文仅一张）。

---

## 2. 全局执行总则

按需选用（每条一句话，可增删）：

1. **阶段门禁制**：未满足出口门禁禁止进入下一阶段，回退记录进进度文件
2. **信息获取决策链**：L1 项目内部 → L2 外部 → L3 用户一次性汇总，不得跳级；触发 L2/L3 记入进度文件决策日志
3. **循环收敛**：修复类循环设最大迭代，超限升级用户，禁止无限循环或静默放弃
4. **单一事实源**：锁定后的 spec（或本文档）为唯一依据；实现中发现规格缺陷必须先回改 spec 再继续
5. **状态续传与可验证完成**：每过一个门禁立即更新进度文件，中断后从进度文件恢复；任何「完成」声明附证据（测试输出、命令结果、文件路径）
6. **subagent 执行制**：调研、实现、审核一律派遣 subagent，主控仅编排（进度维护、门禁判定、派遣协调、升级用户决策）

---

## 3. 阶段详细定义

逐阶段一节，编号连贯：P0, P1, …, P{n-1}（含终验）。标准骨架按任务裁剪：P0 环境与准备 → 调研/设计 → 审核 → 实现（TDD/集成） → 端到端验收 → 终验。

**loop 形态每节结构：**

```markdown
### P{k} {阶段名称}

**步骤**：

1. {动作} → 验证：{检查方式}
2. {动作} → 验证：{检查方式}

**核心产物**：{落盘路径}

**出口门禁**：

- [ ] {可验证门禁1}
- [ ] {可验证门禁2}
```

**graph 形态每节结构（节点版）：**

```markdown
### N{k} {节点名称}

**依赖节点**：{Nx, Ny 或 "无"（并行起点）}
**输入**：{依赖节点的产物}

**步骤**：

1. {动作} → 验证：{检查方式}

**核心产物**：{落盘路径}

**出口门禁**：

- [ ] {可验证门禁}

**回退边**：{门禁不满足时回退到哪个节点重新执行}
```

※ 门禁规则：

- 每条门禁必须可验证（命令、测试、文件存在性、审核结论），禁止「差不多」式表述
- 实现阶段步骤必须含 RED→GREEN→REFACTOR 循环、lint/typecheck/测试校验、进度记录、Conventional Commits；是否强制 TDD 由用户实现要求决定
- WBS 任务清单全文仅一张，置于实现阶段节内（任务ID | 任务目标 | 依赖 | 派遣角色 | 验收标准），任务粒度遵循 1.3，「任务目标」列为一句可验证目标，与 0.3 门禁总表呼应
- 含 `{待调研项}` 的节点/阶段设「回填门禁」：占位符全部回填并记录出处后才可勾选，未回填不得放行依赖该信息的步骤

---

## 4. 派遣规范（subagent 执行制）

调研、实现、审核三类操作由 subagent 派遣完成，主控代理不亲自执行；审核专员独立于实现专员，禁止自我审核。每次派遣必须包含六要素：

```markdown
【角色】调研专员 / 实现专员 / 审核专员（明确单一职责）
【目标】一句话可验证的本次派遣目标（禁止「了解/梳理/协助完成」类泛化描述）
【输入】具体文件路径 / 报告路径 / 上下文说明（禁止模糊指代）
【职责】做什么、不做什么（明确边界）
【输出】产物路径 + 必含内容结构
【完成标准】可验证的退出条件
```

**并行规则**：无依赖并行、有依赖严格串行；并行判定必须经冲突与依赖反思（不写同一文件/资源、无一方产出是另一方输入的隐藏依赖），存疑改串行。graph 形态在此补充并行分支派遣与汇合同步说明。

---

## 5. 完成条件（Definition of Done · 退出唯一依据）

checkbox 清单，每条附证据要求，按任务选用 5~10 条，基线：

- [ ] 任务范围内 {各项} 全部完成，测试全通过（单测/集成/e2e）
- [ ] CI 全绿（如项目有 CI）
- [ ] 代码审核（审核专员）通过
- [ ] 调研、实现、审核全部由 subagent 派遣且派遣记录完整
- [ ] 全部产物已提交 git，终验报告每项附证据

---

## 6. 循环与中止机制汇总

```markdown
| 循环 | 触发条件 | 动作 | 退出条件 | 最大迭代 | 超限处理 |
| --- | --- | --- | --- | --- | --- |
| {修复循环} | {什么情况进入} | {循环内做什么} | {满足什么退出} | {N} | 升级用户（附问题清单与当前状态） |
```

※ 任务含破坏性/外部动作时，在本节补中止条件：需先向用户确认的动作类型（删除数据、对外发布、不可逆操作等）；静默放弃、伪造证据、跳过门禁并入第七章红线。

---

## 7. 红线禁止事项

编号列表（按任务调整，通常含）：

1. 禁止跳过任何阶段门禁，或在出口条件未满足时推进下一阶段
2. 禁止未经测试验证即标记任务或阶段完成
3. 禁止在锁定后偏离 spec 实现（发现规格问题必须先回改 spec）
4. 禁止绕过审核直接合入代码
5. 禁止缩小任务范围、削减功能项或边界测试以换取「完成」
6. 禁止伪造、跳过或选择性运行测试与 CI
7. 禁止在 L1/L2 可调研的情况下直接询问用户
8. 禁止丢弃或重做已完成且有进度记录的阶段
9. 禁止产物仅存于对话上下文而不落盘提交

---

## 8. 用户输入与待调研项（可选，用户未提供相关内容且无占位符时本章省略）

用户提供的信息原样收录（一行一项，不增删语义），并声明「与最高约束文件冲突时以约束文件为准」：

```markdown
- 参考：{名称}（{路径/链接}）→ 用于 {阶段}
- 实现要求：{技术栈/规范/测试与 CI 要求原话或要点} → 落于 {阶段/门禁}
- 协同技能：{技能名} → 触发于 {阶段}（{输入} → {产物}）
- 待调研项：{占位符} → 回填门禁设于 {阶段/节点}
```

※ 协同技能全文档只两处出现：对应阶段步骤尾一句（触发 {技能名}：{输入} → {产物}）+ 本节登记一行，禁止展开其内部流程与原理。
※ 实现要求含覆盖率分级（核心 X% / 非核心 Y%）时，锁定「核心功能清单」的界定方式与时机：首个实现阶段出口门禁前确定并随 spec 落盘，覆盖率门禁以该清单核对。
※ 用户未提供参考/实现要求时，门禁与 DoD 中不得出现凭空编造的技术要求。
